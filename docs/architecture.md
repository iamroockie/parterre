# Parterre — архитектурный документ

Статус: живой документ, обновляется по мере развития проекта.

---

## 1. Что мы строим

Платформа продажи билетов на события с выбором **конкретного места** в зале.
Позиционирование: улучшенная версия Kassir.ru / Ticketland / Афиши.

Ключевое обещание системы:

> Место продаётся **ровно один раз**, и это доказано воспроизводимым
> нагрузочным тестом, а не заявлено в README.

Всё остальное — каталог, оплата, доставка билета — обслуживает это обещание.

---

## 2. Роли и сценарии

**Покупатель**
1. Ищет событие в каталоге.
2. Открывает схему зала, видит свободные и занятые места, цены по категориям.
3. Кликает место → создаётся **бронь (hold)** со сроком жизни 15 минут.
4. Оплачивает. Получает билет с QR-кодом на почту.
5. Не успел оплатить → бронь истекает, место возвращается в продажу.

**Организатор**
1. Заводит площадку и схему зала (секции, ряды, места).
2. Создаёт событие, назначает цены по категориям мест.
3. Открывает продажи (в том числе с отложенным стартом).
4. Смотрит статистику: продано, забронировано, выручка.

**Контролёр на входе**
1. Сканирует QR билета.
2. Получает ответ: пропустить / билет уже использован / билет недействителен.

## 3. Профиль нагрузки

Это не равномерный трафик. Это **пики**.

| Режим | Нагрузка | Что нагружено |
|---|---|---|
| Обычный день | 50–200 RPS | каталог (чтение) |
| Старт продаж на популярное событие | 5 000–50 000 RPS первые 60 секунд | инвентарь (запись, высокая конкуренция за одни и те же строки) |
| Вход на мероприятие | 200 RPS в течение часа | валидация билетов |

Целевые показатели, которые мы будем доказывать замерами:
- ноль случаев овербукинга при любой нагрузке — **жёсткое требование, не обсуждается**;
- p99 чтения схемы зала < 50 мс;
- p99 создания брони < 200 мс.

---

## 4. Границы: чего мы НЕ делаем

- **Не интегрируемся с настоящей платёжкой.** Пишем мок-провайдер, который
  имитирует поведение YooKassa: задержки, дубли вебхуков, отказы, приход
  вебхука раньше ответа на API-запрос. Мок должен быть **злым** — иначе он
  не докажет корректность саги.
- **Не делаем микросервисы заранее.** Начинаем с модульного монолита,
  выносим сервис только тогда, когда для этого есть причина, записанная в ADR.
- **Не делаем Kubernetes.** docker compose закрывает всё, что нужно сейчас.
- **Не делаем возвраты, промокоды, программу лояльности, мобильное приложение.**
  Возможно это попадёт в roadmap.

## 5. Архитектура кода

### 5.1 Модульный монолит

```
cmd/
  api/main.go            — точка входа HTTP API
  worker/main.go         — фоновые задачи (появится вместе с бронями)
internal/
  catalog/               — события, площадки, схемы залов
  inventory/             — места, брони, статусы ← ЯДРО
  order/                 — заказы, конечный автомат
  payment/               — интеграция с платёжным провайдером
  ticket/                — выпуск и валидация билетов
  notification/          — отправка писем
  platform/              — общая инфраструктура:
migrations/              — SQL-миграции (goose)
docs/
  architecture.md        — этот файл
  adr/                   — записи архитектурных решений
tests/
  load/                  — сценарии k6
```

### 5.2 Правила внутри модуля

Каждый модуль устроен одинаково:

```
internal/inventory/
  service.go     — бизнес-логика, не знает про HTTP и про SQL
  repository.go  — работа с PostgreSQL
  http.go        — HTTP-хендлеры, только парсинг/валидация/сериализация
  model.go       — доменные типы
  errors.go      — доменные ошибки модуля
```

**Жёсткие правила связности** (их нарушение — блокирующее замечание на ревью):

1. Модуль **не импортирует репозиторий другого модуля**. Только его публичный
  сервисный интерфейс.
2. Интерфейс объявляется **на стороне потребителя**, а не поставщика. Если 
  `order` нужен инвентарь, то интерфейс `SeatReserver` живёт в пакете 
  `order`, а `inventory.Service` просто ему удовлетворяет. Никаких `interfaces.go` 
  с двадцатью интерфейсами.
3. Зависимости передаются **явно через конструктор**. Никаких глобальных
  переменных, никаких DI-контейнеров с рефлексией.
4. `context.Context` — **первый аргумент** каждого метода, который делает
  ввод-вывод. Всегда. Никогда не хранится в структуре.

Смысл этих правил: когда придёт время выносить `inventory` в отдельный
gRPC-сервис, это будет замена реализации интерфейса, а не переписывание.

## 6. Стек и обоснования

| Что | Выбор | Почему |
|---|---|---|
| Язык | Go 1.27 | цель проекта |
| HTTP | `net/http` + маршрутизатор `chi` | нужны группы маршрутов и цепочка middleware |
| БД | PostgreSQL 18 | нужны транзакции, уровни изоляции, advisory locks |
| Драйвер | `pgx/v5` напрямую, без `database/sql` | нужен доступ к специфике PostgreSQL и к нормальным типам |
| SQL | руками | максимальный контроль SQL и скорость работы |
| Миграции | `goose` | простой, на Go, умеет и SQL, и Go-миграции |
| Логи | `log/slog` | структурированные, без внешних зависимостей |
| Конфиг | переменные окружения + `caarlos0/env` | разбор типов по тегам структуры, без кодогенерации |
| Тесты | `testing` + `testify/require` + `testcontainers-go` | интеграционные тесты против **настоящего** PostgreSQL, а не моков |
| Линтер | `golangci-lint` | обязателен, в CI |
| Нагрузка | `k6` | сценарии на JS, хорошие отчёты |

Появится позже, по мере необходимости: Redis, Kafka, gRPC, OpenTelemetry + Jaeger + Prometheus + Grafana.

## 8. Схема данных: первый набросок

Детали уточняются в задачах, но ключевые сущности и главный инвариант:

```
venues (площадки)
  └── seat_maps (схемы залов: секция / ряд / место)

events (события)
  └── event_seats (место на конкретном событии)
        status: available | held | sold
        price_category_id
        version           ← для оптимистичной блокировки

holds (брони)
  seat_id, order_id, expires_at

orders (заказы)
  status: created | awaiting_payment | paid | cancelled | expired
  idempotency_key

tickets (билеты)
  order_id, seat_id, qr_token, used_at
```

**Главный инвариант системы:**

> Для любого `event_seat` в любой момент времени существует не более одной
> активной брони и не более одного выпущенного билета.

Всё, что делается вокруг покупки, брони и оплаты, существует ради защиты
этой строчки.
