# Работа с git

## Модель ветвления: trunk-based

`main` всегда зелёный и всегда пригоден к деплою. Всё остальное —
короткоживущие ветки под одну задачу из Issues.

```
до слияния     main ──A──B
                         \
                          C──D    feat/6-database

после слияния  main ──A──B──C'──D'
                            └────┘  те же изменения, новое основание
```

`main` остаётся прямой линией: узлов «Merge pull request» в нём нет.
`C'` и `D'` — при слиянии коммиты не переезжают, а копируются с новым основанием, 
и идентификаторы у копий другие. Почему так, а не merge — в разделе ниже.

**Никаких `develop`, `release/*`, `hotfix/*`.** Git-flow решает задачу
поддержки нескольких релизов одновременно; у нас непрерывный деплой и
ровно одна версия в проде, поэтому его ветки — накладные расходы без
пользы.

### Именование веток

`<тип>/<номер issue>-<кратко>` — тип совпадает с типом коммита, номер берётся
из задачи в Issues:

```
feat/6-database
fix/14-pool-leak
perf/28-optimistic-locking
```

### Цикл работы над задачей

```bash
git switch main
git pull                              # ветка отводится от свежего main
git switch -c feat/6-database
# ... атомарные коммиты по ходу работы ...
task check                            # обязательно ДО того, как открыть PR
git push -u origin feat/6-database
```

Дальше на GitHub: открыть pull request и указать в описании `Closes #6` —
тогда задача закроется сама в момент слияния. Дождаться зелёной проверки.
Слить кнопкой **Rebase and merge**.

После слияния ветка удаляется — и на GitHub, и локально:

```bash
git switch main
git pull                              
git branch -D feat/6-database         
```

`-D` - это следствие rebase-слияния: в `main` приехали копии коммитов с другими 
идентификаторами, поэтому `-d` считает ветку неслитой и удалять отказывается. 
Переиспользовать такую ветку под следующую задачу нельзя — заводится новая от свежего `main`.

**Если `main` уехал вперёд, пока PR висел.** GitHub покажет в PR конфликт.
Разрешается он не там, а у себя, ещё одним rebase:

```bash
git switch main
git pull
git switch feat/6-database
git rebase main                       # конфликты разрешаются здесь и только здесь
git push --force-with-lease
```

Открытый PR обновится сам — новый заводить не надо. Кнопкой «Update branch»
на GitHub не пользоваться: она делает merge и оставляет в истории ровно тот
лишний узел, ради избавления от которого всё и затевалось.

`--force-with-lease`, а не `--force`: первый сначала проверяет, что ветка на
сервере там же, где и была последний раз, и отказывается, если туда
успели что-то положить. Второй затирает молча.

## Почему rebase, а не merge

Merge-коммит хранит правду о том, как всё было на самом деле: здесь работа
шла параллельно, здесь сошлась. Иногда эта правда ценна — например, когда
над одной веткой работают несколько человек и важно понимать, кто с чем
сходился. Rebase её выбрасывает сознательно, в обмен на читаемую историю.

Правило выбора:

- **своя незалитая ветка** → rebase, платить нечем;
- **общая ветка, которая уже есть у кого-то ещё** → только merge, иначе
  можно затереть историю дргим разработчикам.

## Сообщения коммитов: Conventional Commits

```
<тип>(<область>): <что сделано в повелительном наклонении>

<зачем это сделано — если неочевидно>
```

Язык — английский. Заголовок до ~70 символов, без точки в конце.

### Типы

| Тип | Когда |
|---|---|
| `feat` | новая функциональность |
| `fix` | исправление поведения |
| `perf` | производительность |
| `refactor` | изменение кода без изменения поведения |
| `test` | тесты |
| `docs` | документация, ADR |
| `ci` | GitHub Actions |
| `chore` | всё остальное |

## Что попадает в один коммит

Один коммит — одно логическое изменение, которое можно откатить целиком,
не сломав ничего вокруг. Каждый коммит в `main` должен собираться.

Это не эстетика. Практическая польза появляется в двух местах:

- **`git revert`** — откатить одну неудачную идею, не трогая остальное;
- **`git bisect`** — впереди эксперименты с блокировками и замеры
  пропускной способности. Когда цифра внезапно упадёт, bisect найдёт
  виновный коммит за пару минут. По истории из `wip`, `fix`,
  `теперь работает` он не найдёт ничего.

Практическое правило: если в заголовок хочется вставить «и» — это два коммита.
